- 新增 worker stuck-loop 防御：L2 stuck detector 在 `frontend_coder` worker 触发「同 path 读 ≥4 次」或「写后连续读 ≥6 次」时立刻 `composedController.abort()` 并打 `sub_agent:worker:stuck_loop:trigger` 事件；过去这种「Minimax-M3 / vilao.ai / 9Router 等 local OpenAI-compatible proxy」确定会卡住的循环只能等满 5 分钟 `per-role ceiling`，现在 abort 时间降到 ≤60s；researcher / reviewer 等没有 write tool 的 role 不会触发 post-write threshold B（`hasWrittenThisAttempt` 永远 false），同 path threshold A 只在 `fs_read_file` 同 path 字面相等时才累加，`fs_list` 无 path 会 reset 计数器，避免误抓合法多文件浏览流程
- 新增 worker file-rescue 兜底路径：L2 stuck_loop abort 后若 `outputFileExists === true`（worker 在 loop 前已经写完文件），用单独的 `synthesizeStuckLoopHandoff` helper 合成最小 success handoff（`status:'success'` + `output_file` + 标注「stuck-loop detected, output file authoritative」），让 `assembleHandoff` 走 branch 6 success 路径。Summary / handoff_notes 文案与 `synthesizeSilentWriteHandoff`（Subtask 8.8 Fix Y）刻意区分，方便 debug log grep 时区分两种 fallback 路径；`failureReason='stuck_loop'` 在 `assembleHandoff` branch 1 retryable override 里被显式排除（deterministic 行为，retry 不会改变结果）——`shouldRetry` 因 gated on `retryable !== true` 零改动自动 false。L3 rescue 路径同时把 `readOutputIfAny` 拿到的 `r.content` 挂到 `output_content`（之前只读 `r.exists` 把 `content` 丢掉了），主代理 `--- output_content (...) ---` marker 能渲染出 worker 实际写的产物，与 silent-write fallback 行为对齐。若 loop 在写之前就触发（无 file 可救），catch block 文案改为「Worker aborted: stuck-loop detected …」而不是误导性的「Worker timed out after Xms」，看 debug log 时一眼能区分是 model loop 触发 detector 而不是 ceiling 烧满
- New `stuck_loop` defense for workers: the L2 stuck detector aborts the `frontend_coder` runner and logs `sub_agent:worker:stuck_loop:trigger` the moment it sees either "≥4 reads of the same path" or "≥6 consecutive reads after a write". Previously this deterministic loop pattern seen with local OpenAI-compatible proxies (Minimax-M3 via vilao.ai / 9Router) had to burn the full 5-minute `per-role ceiling`; abort now lands within ≤60s. Researcher / reviewer never trip the post-write threshold B (their `hasWrittenThisAttempt` stays `false`); the same-path threshold A only counts literal `fs_read_file` path equality, and `fs_list` without a path resets the counter — legal multi-file browsing flows are not falsely caught
- New file-rescue fallback for stuck workers: when L2 stuck_loop aborts and the output file is already on disk (worker wrote it before looping), a dedicated `synthesizeStuckLoopHandoff` helper synthesizes a minimal success handoff (`status:'success'` + `output_file` + a note flagging "stuck-loop detected, output file authoritative") and feeds it through `assembleHandoff`'s branch 6 success path. The summary / handoff_notes text is deliberately distinct from `synthesizeSilentWriteHandoff` (Subtask 8.8 Fix Y) so debug log greps can tell the two fallback paths apart. `failureReason='stuck_loop'` is explicitly excluded from `assembleHandoff`'s branch 1 retryable override (deterministic behavior — retry would not change the outcome); `shouldRetry` is gated on `retryable !== true`, so it returns `false` automatically with zero changes. The L3 rescue path also attaches `output_content` from `readOutputIfAny` (now captures `r.content` instead of only `r.exists`), so the main agent sees the rescued file's body via the `--- output_content (...) ---` marker — symmetric with the silent-write fallback's behaviour. When the loop fires before any write (no file to rescue), the catch block now reports `"Worker aborted: stuck-loop detected …"` instead of the misleading ceiling-style "Worker timed out after Xms" message, so users looking at the debug log know the root cause is a model loop, not the role's per-attempt ceiling

- Knowledge (RAG): New agentic `rag_search` tool (Subtask 4, opt-in). `RagSettings` gains `ragSearchEnabled` (default OFF). When on, the main agent can call `rag_search({ collection, query, limit })` mid-conversation to run a hybrid (vector + BM25 / RRF) query against the named collection — complementing the send-time pre-injected top-5 chunks when the user asks for a specific section number, function name, or code identifier that the envelope does not cover. The tool returns a structured `<rag-search-result>` envelope (`collection` / `query` / `count` + `<chunk source index score context>`), XML-escaped for parseable downstream consumption. `limit` defaults to 5 and caps at 20; the `score` attribute is RRF-fused (ordering-only, not a probability). Belt-and-braces safety: `execute()` re-reads settings and throws if disabled, so a stale session whose tool list still includes `rag_search` cannot actually invoke it after the user toggles off; `lib/tools/index.ts` only pushes the tool into the session's array when `ragSearchEnabled` is true. When off, the tool is absent from both the tool list and the system prompt — the LLM has no way to hallucinate a call. System-prompt augmentation uses `{{RAG_SEARCH_TOOL_LINE}}` and `{{RAG_SEARCH_WORKFLOW_STEP}}` placeholders, wired through `entrypoints/background/agent/prompt-composer.ts`. When off, both resolve to `''` and `collapseTripleNewlines` collapses the resulting triple-newline runs so the prompt is byte-identical to pre-Subtask-4, preserving Anthropic prompt caching

- Knowledge (RAG): Contextual Retrieval (Subtask 3, opt-in). `RagSettings` gains four new fields — `contextualRetrievalEnabled`, `contextualLlmBaseUrl`, `contextualLlmApiKey`, `contextualLlmModel` — all OFF by default, with the endpoint defaulting to the local CLIProxyAPI. When enabled, the indexer inserts a `context-generation` phase between chunking and embedding: each chunk is shipped to a cheap LLM that produces a ≤ 40-word context prefix. The prefix is prepended to the embed input **and** stored in `metadata.context_prefix`; the Subtask 2 `content_tsv` expression already picks it up via `COALESCE`, so the BM25 path gains the recall boost with no migration. Long documents (> 40K chars) use a slim envelope (title + outline + 1–2 surrounding paragraphs) capped at 8K chars. LLM failures / empty responses gracefully degrade to `''` — the chunk still indexes, it just loses the recall boost for that one chunk — at concurrency 8. `contextualLlmApiKey` is classified as a secret in the backup registry (same shape as `embedderApiKey`) and follows merge / replace strategy on restore
